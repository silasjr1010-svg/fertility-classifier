## 1. System Overview

**Q: What does this system do?**
A: It's a Streamlit web app that classifies chicken egg photos in two stages: Stage 1 checks *"is this even an egg?"* (binary), and Stage 2 (only if Stage 1 says yes) classifies the egg as **fertile**, **infertile**, or **dead**. Source: `app.py`'s prediction pipeline and `label_mapping.json`.

**Q: What's the tech stack?**
A: Streamlit for the UI, TensorFlow/Keras for the CNNs, `Pillow`/`NumPy` for image handling, `pandas` for label bookkeeping. Pinned in `requirements.txt` (`streamlit==1.32.0`, TensorFlow, etc.).

**Q: Why two separate models instead of one?**
A: A two-stage design avoids the classifier confidently mislabeling a non-egg object as "fertile/infertile/dead" — Stage 1 acts as a gatekeeper. This is a system design choice; not documented anywhere as a stated requirement, but it's evident from the architecture.

**Q: Is there authentication?**
A: Yes — `users.json` defines a simple username/password login checked in `app.py` before the upload/predict UI is shown.

## 2. Data & Labels

**Q: Where does training data come from?**
A: A Kaggle dataset, `hlnkmb/chicken-egg-analysis-dataset`, referenced in the training notebook via `kaggle datasets download`. It is **not bundled in the repo** — you must fetch it separately.

**Q: What format are the labels in?**
A: An `info.labels` JSON file inside the dataset, with a `files` list of `{path, label}` entries. The notebook parses this into a pandas DataFrame (`df`).

**Q: What are the class labels, and how are they indexed?**
A: `label_mapping.json` → `{"dead": 0, "fertile": 1, "infertile": 2}`. This is alphabetical ordering of the three unique labels, computed the same way in both the training notebook and matched by the app at inference time.

**Q: Where do "negative" (non-egg) samples for Stage 1 come from?**
A: They're synthetically generated by cropping the four corners of existing egg images (30% of the dataset size) — there's no separate "non-egg" image collection. This is a training-pipeline detail, not a documented requirement, and it's worth knowing because it means the detector has never seen *real* non-egg photos (kitchen counters, hands, other objects) — only cropped corners of egg photos.

**Q: Are the CSVs (`labels_table.csv`, `stage1_detection.csv`) in the repo used?**
A: No — they're stale leftovers from a prior Windows run (their paths use `Dataset\testing\...` backslashes). The training script regenerates its own label tables fresh each run; the committed CSVs are not read by any code path.

## 3. Model Architecture

**Q: What CNN architecture is used?**
A: MobileNetV2 (`tf.keras.applications.MobileNetV2`), pretrained on ImageNet, used as a **frozen** feature extractor (`base_model.trainable = False`) for both stages, topped with `GlobalAveragePooling2D → Dropout → Dense(128, relu) → Dropout → output layer`.

**Q: Why MobileNetV2 specifically?**
A: Not documented, but it's a common choice for lightweight transfer learning — small enough to train fast on limited data/compute (like Colab's free tier) while still leveraging strong pretrained features.

**Q: What's the output layer for each stage?**
A: Stage 1 (detector): `Dense(1, sigmoid)` — binary egg/non-egg. Stage 2 (classifier): `Dense(num_classes, softmax)` — 3-way fertility classification.

**Q: What loss functions and optimizer are used?**
A: `binary_crossentropy` for Stage 1, `sparse_categorical_crossentropy` for Stage 2, both with the `adam` optimizer — standard, appropriate choices for each task type.

**Q: What image size and batch size does training use?**
A: 224×224 input images (matching MobileNetV2's expected input), batch size 16.

**Q: Are there training safeguards against overfitting?**
A: Yes — `Dropout` layers (0.3 and 0.2) plus `EarlyStopping` (`monitor='val_loss', patience=5, restore_best_weights=True`) and `ModelCheckpoint` saving only the best `val_accuracy` epoch.

## 4. Known Errors & Issues (found during analysis)

**Q: Do the shipped `.h5` model files actually work?**
A: No. All four (`egg_detector_best/final.h5`, `fertility_classifier_best/final.h5`) are **133-byte Git LFS pointer stubs**, not real weight files — a side effect of downloading the repo as a ZIP from GitHub instead of `git clone`-ing with LFS support. `app.py`'s `load_model()` calls will fail on these as-is.

**Q: Did the original training notebook actually finish running?**
A: No. Its execution history shows the "Train Stage 1 Detector" cell (execution #2) failing with `NameError: name 'train_test_split' is not defined`, and the "Prepare Stage 2 Labels" cell (execution #1) failing with `NameError: name 'df' is not defined` — both because they ran *before* the imports/data-loading cells (classic out-of-order Jupyter execution). Every cell after that, including the actual `model.fit()` and `model.save()` calls, has no execution record at all.

**Q: Can `untitled8.py` be run as a plain Python script?**
A: No — its first line is `!pip install ...`, a Jupyter/Colab magic command, which is a `SyntaxError` outside a notebook cell.

**Q: Are there any security concerns?**
A: `users.json` stores login passwords in plaintext (`admin123`, `eggpass`, `demo123`). Fine for local prototyping; a real risk if this app is ever deployed somewhere shared or public.

**Q: Any forward-compatibility risks?**
A: `app.py` uses `st.image(..., use_column_width=True)`. This works with the pinned `streamlit==1.32.0`, but that parameter was removed entirely in Streamlit 1.61.0+ — upgrading streamlit without re-pinning would break the app.

## 5. The Fixed Colab Notebook (this session's deliverable)

**Q: What did the rebuilt notebook (`egg_analysis_cnn_training.ipynb`) fix?**
A:
- Reorders cells so imports → data loading → training happens strictly top-to-bottom (fixes the `NameError` crashes)
- Adds an explicit Kaggle dataset download step, pre-filled with `hlnkmb/chicken-egg-analysis-dataset`
- Saves checkpoints to Google Drive so a disconnect doesn't lose progress
- Uses **separate** `EarlyStopping` callback instances per training stage, instead of reusing one object across both `model.fit()` calls (a subtle bug in the original where callback state from Stage 1 could leak into Stage 2)

**Q: What do I still need to do myself?**
A: Upload your own `kaggle.json` (from Kaggle account → Settings → API → Create New Token) when the notebook prompts for it, enable a GPU runtime in Colab, and run the cells in order. After training, download the resulting real `.h5` files and drop them into the app folder, replacing the broken LFS-pointer files.

**Q: Will this guarantee good model accuracy?**
A: Not documented/guaranteed — the notebook fixes the *execution* problems (things that would crash or silently fail), not the *data quality* problem. Model accuracy still depends on the real dataset's size/balance and how well the synthetic corner-crop negatives generalize to real non-egg images, which isn't something code alone can fix.
